# Личные дашборды менеджеров по развитию и сопровождению

## Что реализовано

В кабинетах менеджеров по развитию и сопровождению предусмотрен раздел **«Личный дашборд»**
(`/admin/manager-dashboard`). Администратор и TOP-администратор в этом разделе
видят две вкладки: **«Менеджеры по развитию»** и **«Менеджеры по сопровождению»**.
В каждой — свой HTML, история публикаций и список менеджеров. Клиент доступа к разделу не получает.
Проверка почты, ручная загрузка снимков и журнал импорта общие для обеих групп.

Общий интерфейс и личные данные хранятся независимо:

- **HTML** — отдельная опубликованная версия для каждой группы менеджеров.
  Группу выбирает текущая роль учётной записи: `manager` → `development`,
  `support_manager` → `support`. Менеджер не может выбрать чужую группу через URL.
  Новая загрузка создаёт черновик; публикация и возврат предыдущей версии
  выполняются отдельно с подтверждением. Предпросмотр не подгружает личные
  данные менеджеров. Поддерживается контракт личного дашборда `kts-personal v1`,
  совместимый с предоставленным HTML v12, а не произвольный TOP-дашборд.
  Опубликованный HTML своей группы виден любой активной учётной записи менеджера,
  **даже без email или личного снимка**. Пустой/неоднозначный email, отсутствие
  файла или истёкший срок снимка показывают пояснение в HTML, а не закрывают его.
  Пока нет доступного снимка, поля открытия данных отключены; запрос байтов
  личного файла не выполняется. Пустые данные не выдаются за нулевые показатели.
- **Снимки `.ktsp`** — отдельные зашифрованные файлы, история и текущая версия
  каждого менеджера. Обновление или откат HTML **не удаляет и не сбрасывает**
  личные снимки. Выбор архивного снимка для просмотра не делает его текущим.

В открытой вкладке периодическая проверка и возврат фокуса могут показать
«Доступна новая версия». Уже открытый отчёт не перезагружается принудительно:
менеджер сам открывает обновление. После перезагрузки пароль снимка вводится снова.
Исключение — смена группы менеджера, email или утрата однозначной привязки: очередная проверка
сразу закрывает ранее расшифрованный отчёт, оставляя доступным общий HTML.

Этот документ описывает подготовленную реализацию и её проверки. Наличие кода
не означает, что выполнен push, production-деплой, загружен исходный HTML или
включён почтовый импорт.

Миграция разделения HTML сохраняет существующие версии и текущую публикацию
в группе развития. Группа сопровождения первоначально пустая: администратор
должен загрузить и опубликовать её собственный совместимый HTML. Никакие снимки,
старые прайсы или существующие публикации при этой миграции не удаляются.

## Привязка по emailHash

Используется существующий email из карточки менеджера. Нового поля email и
нового идентификатора сотрудника для текущих файлов не требуется.

В точности как в исходном HTML, вычисляется:

```text
emailHash = Base64(SHA-256(UTF-8(email.trim().toLowerCase())))
```

Это стандартный Base64, не hex и не Base64URL. Не удаляются точки и `+суффиксы`,
не заменяются домены и не угадывается адрес по ФИО. Пробельные символы по краям
нормализуются правилами JavaScript `trim`, включая Unicode-пробелы.

При импорте требуются все условия:

1. Файл имеет допустимый формат личного снимка.
2. Его `emailHash` совпадает с email **ровно одной активной учётной записи
   менеджера по развитию или сопровождению**. Уникальность проверяется сразу
   среди обеих групп: одинаковый email у двух активных менеджеров блокирует
   автоматическое назначение, даже если их роли различаются.
3. Снимок проходит проверки дат, повторов, конфликтов и лимитов.

После этого файл сохраняется с постоянным внутренним `manager_id` из базы.
ФИО и название файла служат подписью для человека, но не определяют получателя.
Переименование файла само по себе не переносит его другому менеджеру.

При отсутствии совпадения получается статус `unknown`, при нескольких —
`ambiguous`; автоматического назначения по похожему имени нет. Администратор
исправляет email в обычных карточках менеджеров либо просит отправителя выпустить
файл на правильный email. Следующая проверка того же письма повторяет попытку
для `unknown`, `ambiguous` и `quota`; можно также повторно загрузить файл вручную.
Для почтового повтора письмо должно оставаться в окне сканирования INBOX.

При каждом чтении снимка сервер заново проверяет владельца, активность,
роль, текущий email и его уникальность. После смены email старый файл с другим
отпечатком не выдаётся. Передача чужого ID снимка не даёт доступа к нему:
ID менеджера берётся из проверенной сессии, а не из параметра запроса.

**emailHash — признак получателя, а не подпись отправителя и не разрешение
на доступ.** Его наличие не доказывает подлинность письма или содержимого.

## Пароль и проверка содержимого

Менеджеру автоматически подставляются его файл и email. Для открытия остаётся
**пароль личного снимка** — не пароль почты и не пароль входа в кабинет.
Пароль не передаётся на сервер, не сохраняется в базе, HTML-версии, журнале
или браузерном постоянном хранилище.

Сервер проверяет незашифрованный заголовок: `fmt=kts-personal`, `v=1`, тип `gz`,
метаданные, календарные даты, канонический Base64, размеры соли/IV/отпечатка,
PBKDF2 с SHA-256 и числом итераций 200 000–600 000. После сохранения проверяются
размер файла и SHA-256 перед выдачей его байтов.

**Успешный импорт означает, что принята оболочка файла, но не означает успешную
расшифровку или проверку расчётов внутри.** Без пароля сервер не может проверить
AES-GCM и понять, правильные ли зашифрованы данные. Это выполняется в браузере
после ввода пароля: дополнительно сверяются внутренние email и даты, структура
данных и лимит распаковки 128 МиБ. Неверный пароль, повреждённое шифрованное
содержимое или несовпадающие внутренние метаданные не открывают отчёт.

HTML исполняется в изолированном iframe с ограничениями сети и доступа к
родительскому кабинету. Проверка HTML-контракта не является доказательством
безвредности произвольного JavaScript; публиковать следует только доверенные,
проверенные версии. Администратор через этот раздел видит метаданные импорта,
но не получает API-доступ к расшифровке чужих личных данных.

Динамические обработчики вкладок и разрезов исходного v12 разрешены конечным
набором CSP-хешей; `eval`, произвольные inline-обработчики и всплывающие окна не
разрешаются. Если следующая HTML-версия меняет интеграционные функции, имена
вкладок или формируемые обработчики, перед публикацией потребуется проверить
совместимость и при необходимости обновить адаптер. Предпросмотр без снимка
показывает форму входа, но не заменяет тест всех разделов с тестовыми данными.

## Первый ввод в эксплуатацию

После согласованного выкладывания кода и успешной миграции:

1. Проверить активность менеджеров в существующих карточках. Для привязки личных
   снимков дополнительно проверить email: он должен совпадать с тем, на который
   исходная программа выпустила `.ktsp`. Для просмотра самого HTML email не нужен.
2. Войти администратором/TOP-администратором и открыть **«Дашборды менеджеров»**.
3. Выбрать нужную группу и загрузить её доверенный совместимый HTML через **«Загрузить черновик»**.
4. Открыть **«Предпросмотр»**, затем **«Опубликовать группе»**. Пока выполнена только
   загрузка черновика, менеджеры не получают новую версию. Изменение публикации
   другим администратором требует обновления страницы перед повторной попыткой.
   Публикация и возврат HTML затрагивают только выбранную группу.
5. В **«Общая загрузка личных файлов»** вручную загрузить один или несколько `.ktsp`.
   Можно смешивать файлы обеих групп: выбранная вкладка HTML не меняет получателя снимка.
   Интерфейс принимает до 32 файлов за операцию, 8 МиБ на файл и 63 МиБ суммарно;
   серверный multipart-лимит — 64 МиБ с заголовками. Результат показывается
   отдельно для каждого файла. Ошибка формата одного вложения не отменяет
   корректные файлы этого пакета.
6. Под настоящей учётной записью менеджера проверить подстановку файла и
   самостоятельный ввод пароля снимка. Не просить пересылать пароль в чат,
   журнал или репозиторий.
7. Для следующего HTML повторить загрузку черновика, предпросмотр и публикацию.
   Кнопка **«Вернуть группе»** публикует предыдущий HTML, оставляя снимки на месте.

Исходные частные HTML/KTSP из пользовательской папки не добавляются в Git и
не публикуются автоматически самим наличием этой реализации.

## Почта: подготовлена, по умолчанию выключена

Предусмотрен отдельный обработчик, способный разобрать, например, одно письмо
с 11 файлами и распределить каждое вложение независимо. Снимки развития и
сопровождения могут приходить вместе в одном письме на тот же ящик от
согласованного отправителя. Второй таймер, ящик или отдельное расписание не нужны.
Настройки существующего
почтового подключения могут использоваться повторно; это не меняет действующий
импорт Excel-остатков.

**До согласования точного адреса отправителя и установки расписания почтовую
автоматику не считать работающей.** По умолчанию `MANAGER_DASHBOARD_MAIL_ENABLED`
выключен. Нужен явный `MANAGER_DASHBOARD_MAIL_ALLOWED_FROM`; общие доменные
шаблоны и подбор отправителя по отображаемому имени не используются.

Полные параметры, ограничения, безопасный ручной запуск и предлагаемое,
но не установленное автоматически расписание описаны в
[инструкции почтового обработчика](../ops/manager-dashboard/README.md).
Остатки `.xlsx` и снимки `.ktsp` следует отправлять отдельными письмами:
существующий импорт остатков перемещает письмо целиком.

Ожидаемый срок обновления в интерфейсе — **10:00 МСК**. Дата файлов и статусы
«нет данных», «устарели», «срок истёк», «актуальны» отображаются по Москве.
Эти подписи сами по себе не отправляют уведомление о непоступившем к 10:00 файле;
отдельное уведомление о пропуске доставки не реализовано. Доставку к указанному
часу нельзя гарантировать, если письмо поступает ровно в 10:00.

## Повторы, даты и ошибки

| Ситуация | Результат |
| --- | --- |
| Повторное письмо/вложение или те же байты под новым именем | Новая версия не создаётся; статус `duplicate` |
| Email не найден / найден неоднозначно | `unknown` / `ambiguous`; файл никому не назначается |
| Дата выпуска старше текущего снимка того же получателя | `stale`; текущий файл сохраняется |
| За ту же дату пришли другие байты | `conflict`; автоматической перезаписи нет |
| Дата выпуска в будущем по Москве | `invalid`; файл не становится текущим |
| Срок действия истёк | `expired`; файл не становится текущим |
| Сохранённый файл позже истёк | Метаданные видны, открытие/выдача байтов запрещены до получения свежего файла |
| Повреждённый заголовок или недопустимые параметры | `invalid`; данные остальных менеджеров не изменяются |
| Превышен лимит хранения | `quota`; последняя принятая копия остаётся на месте |

У `.ktsp v1` дата выпуска имеет точность до дня. Пока нет номера ревизии или
подписанного времени выпуска, сервер не угадывает, какая из двух разных версий
за один день правильная. Для конфликтующего файла требуется разбор и согласованное
переиздание; кнопки принудительной подмены текущего снимка в этой версии нет.

Журнал хранит до 5 000 последних записей, административный обзор показывает
последние 200. В нём — безопасные коды, имя файла, отправитель, время и результат,
без паролей, содержимого шифротекста или исходных ошибок почтового сервера.
Непринятые файлы не сохраняются в отдельный архив приложения: для повторной
обработки нужны оригинал письма или исходный файл.

## Хранение и резервные копии

На одного менеджера установлены пределы **32 версии и 128 МиБ**. Один `.ktsp` —
до **8 МиБ**. Квота вмещает 14 ежедневных файлов предельного размера (112 МиБ)
с запасом для следующей атомарной замены. При успешном импорте удаляются допустимые старые версии, полученные
более **14 × 24 часов назад**, но сохраняются текущая и предыдущая принятые
копии. Последняя копия не исчезает из-за одного только истечения 14 дней.
Очистка запускается при принятии следующего файла; это не обещание удаления
строго в момент достижения 14 суток. Если оставшиеся версии не помещаются
в квоту, новый импорт отклоняется, а старые данные не удаляются ради него.

Для HTML каждой группы отдельно: **5 МиБ на файл, 50 версий и 100 МиБ суммарно**. HTML-история
не очищается автоматически; при достижении предела нужна отдельная согласованная
процедура удаления ненужных версий. Опубликованную версию нельзя считать
заменяемой простым удалением файла на диске.

Используются отдельные таблицы PostgreSQL:

- `personal_dashboard_html_versions` и `personal_dashboard_html_state`;
- `personal_dashboard_snapshots` и `personal_dashboard_snapshot_state`;
- `personal_dashboard_imports`.

HTML хранится в закрытой таблице, исходные зашифрованные байты `.ktsp` — в `bytea`.
Новых публичных каталогов и файловых путей для снимков нет. Полный дамп базы
PostgreSQL существующего механизма резервирования включает эти таблицы после
применения миграции. Поэтому восстановление соответствующего полного дампа
возвращает HTML, снимки, назначения, историю и журнал. Снимки, поступившие после
даты выбранной копии базы, в ней отсутствуют.

В базе и её бэкапах **нет паролей снимков**, без них восстановленный `.ktsp`
по-прежнему не расшифровать. Для восстановления всей системы отдельно нужны
код, закрытая конфигурация, доступ к зашифрованным облачным копиям и сохранный
KMS-ключ — см. [инструкцию резервирования проекта](../ops/backup/README.md).
Файлы из исходной локальной папки сотрудника и вся история почтового ящика не
становятся частью бэкапа проекта только из-за подключения почтового импорта.

## Проверки

Локальные проверки без доступа к почте и production:

```bash
node --import tsx --test tests/manager-dashboard-domain.test.ts
npm test
npx tsc --noEmit --incremental false
```

Для проверки схемы и транзакций предусмотрен отдельный скрипт:

```bash
bash scripts/test-personal-dashboard-postgres.sh
```

Он требует доступных серверных утилит PostgreSQL (`KTS_TEST_PG_BIN` при другом
пути), непривилегированного пользователя и предварительной оценки ресурсов.
Сам создаёт временный кластер с Unix-сокетом, **без TCP-listener**, отдельной
непривилегированной ролью `personal_app` и базой `kts_personal_integration`.
Он заменяет значение `DATABASE_URL` только для своего процесса, не читает
production-строку подключения и удаляет только собственное временное окружение.
Сам интеграционный тест дополнительно требует `KTS_PERSONAL_TEST=1`, точное имя
тестовой базы/роли, временный socket-путь и пустую исходную схему.

В изолированном PostgreSQL **16.15** под Node.js **24.19.0** успешно выполнены
все **15 групп SQL-проверок** (16 успешных тестов вместе с родительским):
полная новая миграция и обновление прежней схемы с сохранением публикаций,
смешанный пакет обеих ролей из 11 файлов с одной ошибкой, владение/смена email/
неактивность/роли, HTML без email/снимка и с неоднозначным email при запрете выдачи
личного файла, конкурентные повторы, повтор после исправления
получателя, порядок дат и конфликты, HTML-публикация/откат без потери снимков,
независимые публикации/откаты и квоты HTML двух групп, запрет межгрупповых ссылок,
14-дневная очистка, квота 32 версий снимков, безопасный журнал и штатное удаление только
созданного тестового менеджера с каскадом его записей. Временный кластер остановлен
и убран; рабочая база и настоящие менеджеры не использовались.

Для сравнения исходного HTML с интегрированным на синтетических зашифрованных
данных есть отдельная необязательная браузерная проверка; команда и ограничения
приведены в [почтовой инструкции](../ops/manager-dashboard/README.md#изолированная-браузерная-проверка).
На предоставленном v12 Chromium и WebKit прошли сравнение KPI и контрольных
показателей, всех вкладок, разрезов, фильтров и сбросов, пароля и расшифровки,
изоляции iframe, блокировки всплывающих окон и выгрузки XLSX через родительский
мост. Два предоставленных настоящих `.ktsp` прошли проверку оболочки только
для чтения; их содержимое не расшифровывалось и на сайт не загружалось.
Дополнительные регрессионные проверки покрывают опубликованный HTML без email,
с неоднозначным email, без снимка и с истёкшим снимком: реальный React-компонент
создаёт обычный менеджерский iframe, а Chromium/WebKit показывают исходный v12

расчётов по синтетическому файлу также проходят.
Запуск `scripts/import-manager-snapshots.ts`, напротив, является **настоящим
импортом**, а не тестом сборки: он допустим только после согласования почтовой
конфигурации и источника файлов.
