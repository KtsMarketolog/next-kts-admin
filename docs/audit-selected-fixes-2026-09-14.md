# Исправления выбранных пунктов аудита — 14.09.2026

## Сохранность старых прайсов

Установка этих исправлений не удаляет и не пересоздаёт существующие прайсы,
публичные ссылки, товары, скидки и ручные цены. Новая миграция
`202609140002_personal_dashboard_mail_receipts` только создаёт отдельную таблицу
служебных отметок успешного почтового импорта и её индекс.

Рабочие прайсы и остатки ради проверки не сохранялись/не импортировались.
Регрессионные проверки работают на синтетических данных в отдельных временных
PostgreSQL-кластерах без TCP и без production DATABASE_URL.

Обычное редактирование после установки продолжает применять выбор менеджера:
скрытые позиции остаются скрытыми, а действительно удалённые из переданного
состава позиции удаляются только из редактируемого прайса. Сами старые прайсы
не очищаются ни миграцией, ни новым почтовым механизмом.

## Что исправлено

1. **Остатки: неизвестный заголовок количества.** Файл без распознанных
   обязательных колонок отклоняется до обновления товаров. Пустая ячейка
   количества в корректно распознанной колонке, как и раньше, означает 0.
2. **Остатки: ошибка одного склада.** Если хотя бы одна строка артикула содержит
   неверное количество, весь агрегат этого артикула исключается из обновления.
   Прежние общий/складские остатки и сопутствующие поля сохраняются независимо
   от порядка строк. Другие корректные артикулы обрабатываются; ошибка видна
   в результате частичного импорта.
3. **Обрезание Excel-каталога.** Признак SheetJS `!fullref` выявляет чтение только
   части листа; такой XLSX/XLS отклоняется до полной замены каталога. Включён
   тест маленького разреженного файла с поздним товаром за границей чтения.
4. **Корзина после пересохранения.** Позиции обновляются по устойчивой паре
   «товар + вариант» с сохранением ID и исторических полей. Обычное изменение
   комментария/настроек больше не делает все ID открытой корзины устаревшими.
   Если выбранный товар действительно удалён или скрыт, интерфейс объясняет
   изменение состава. Формулы цены и проверки доступности не ослаблены.
5. **Обновления чата.** SSE остаётся быстрым каналом, но не единственным.
   Видимая вкладка повторно читает авторизованные API через 15 секунд после
   завершения предыдущей синхронизации, при возврате фокуса, восстановлении
   сети и переподключении SSE. Это покрывает пропущенные события другого
   процесса PM2 без новой инфраструктуры. Запросы ограничены таймаутом,
   выполняются без наложения в рамках подписки и отменяются при уходе со
   страницы. Скрытая/offline-вкладка не опрашивает API. Черновики форм не
   перезаписываются фоновыми данными. Отправка чата освобождает кнопку после
   сетевой ошибки; автоматической повторной отправки сообщений нет.
6. **Аналитика и скидки.** Менеджерская аналитика учитывает только видимые
   позиции. Группа 10% + 0% теперь отображается как «Разная», 100% — как 100%.
   Нулевая конечная цена отличается от отсутствующей цены. Исправлены отчёты,
   а не сохранённые значения скидок в старых прайсах.
7. **Повторное скачивание личных снимков.** Перед DOWNLOAD проверяется
   долговременная отметка аккаунта/папки/UIDVALIDITY/UID/MIME-части.
   Она создаётся только после подтверждённого успешного импорта или успешного
   дубликата. Ошибки загрузки, неизвестный/неоднозначный получатель, квота и
   другие неуспешные исходы такой отметки не получают и могут повторяться.

## Почтовые отметки: ограничения и восстановление

- Таблица `personal_dashboard_mail_receipts` содержит хеш транспортной
  идентичности, ключ импорта, ID менеджера, emailHash и время. Паролей,
  открытых почтовых адресов и содержимого снимков в ней нет.
- Отметки старше 30 дней удаляются только из этой таблицы. Это дольше
  максимального окна почтовой проверки 14 дней. Снимки, прайсы и диагностический
  журнал таким удалением не затрагиваются.
- После первого обновления старые письма могут быть скачаны ещё один раз,
  чтобы создать отметки. Последующие проверки пропускают успешные вложения.
- Потеря отметки или авария между сохранением снимка и отметки приводит к
  безопасному повторному скачиванию/проверке дубликата, а не потере снимка.
- Смена UIDVALIDITY, аккаунта, папки или UID не даёт использовать старую
  отметку для другого вложения. Проверка разрешённого отправителя остаётся
  до проверки отметки; IMAP открывается только для чтения.
- Неизвестные/неоднозначные импорты допускают повтор после исправления email.
  Уже успешно назначенный снимок не переназначается автоматически другому
  сотруднику при переносе email: прежняя защитная семантика сохранена.
- По-прежнему действуют ограничения размера отдельного снимка и письма,
  последовательная обработка вложений и ограничение сложности MIME. Этот
  фикс устраняет лишние скачивания, а не снимает защиту памяти.

## Проверка перед публикацией

```sh
npm test
npx tsc --noEmit --incremental false
npm run lint
npm run build:webpack
bash scripts/test-wholesale-price-postgres.sh
bash scripts/test-personal-dashboard-postgres.sh
```

Последние две команды требуют PostgreSQL 16 и запускаются только через
предоставленные защитные скрипты. Проверены 20 001 позиция, сохранение ID/ссылок,
нетронутый другой старый прайс, откат ошибочного обновления, параллельные записи,
миграция почтовых отметок, действующая привязка к email и сохранение снимка после
очистки старой отметки. Почтовые unit-тесты проверяют отсутствие второго DOWNLOAD
и повтор неуспешного вложения без доступа к настоящему ящику.

Результат локальной проверки: 280/280 общих тестов, TypeScript и production-сборка
успешны. ESLint: 0 ошибок, 37 существовавших предупреждений. На изолированном
PostgreSQL 16.15 прошли 10 сценариев прайсов и 12 сценариев личных дашбордов.
Эти результаты не означают, что исправления уже опубликованы на рабочем сайте.

## Что не входит

Остальные пункты аудита, включая прямую раздачу документов через Nginx,
доверие браузерному курсу валют, старую гонку почтового импорта остатков,
числовую нормализацию каталога и очистку осиротевших файлов TOP, не менялись.
Для них требуется отдельная работа. Рабочее облако и расписания не изменялись.
