# Большие файлы данных TOP-дашбордов

Публичный предел потоковой загрузки данных — 500 МиБ. Приложение принимает такой
запрос через `stream-v1` и сразу пишет его в защищённое файловое хранилище. Один
процесс не держит весь файл в памяти.

У старого multipart-режима отдельный предел 100 МиБ, а у распакованного JSON в
gzip — 2 ГиБ. `experimental.proxyClientMaxBodySize` в `next.config.ts` следует
оставлять равным `101mb`: повышение этого значения заставит Next.js буферизовать
слишком большие запросы в памяти.

На Nginx увеличенный предел должен действовать только для маршрута загрузки:

```nginx
location ~ ^/api/admin/top-dashboard/blocks/[1-9][0-9]*/data/?$ {
    client_max_body_size 501m;
    client_body_timeout 10m;

    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_request_buffering off;
    proxy_read_timeout 10m;
    proxy_send_timeout 10m;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

`501m` оставляет место для служебного контейнера вокруг файла размером до
500 МиБ. Общий предел виртуального хоста можно оставить низким для остальных
маршрутов.

История HTML и данных расположена внизу страницы, после предпросмотра.
Верхняя часть оставлена для текущих данных, загрузки и действий последнего черновика.

После успешной публикации/отката сохраняются **действующий и предыдущий рабочие
HTML**, а также все неопубликованные черновики. Для данных сохраняются **текущая
и предыдущая рабочие версии** в каждом совместимом контексте: универсальный
набор привязан к точному HTML, встроенный формат — к своему типу отчёта.
Данные предыдущего HTML не удаляются ради данных нового, иначе откат был бы пустым.
Это может означать больше двух физических файлов на блок. Новые черновики не
вытесняют рабочую историю или другие черновики; при квоте HTML загрузка отклоняется.
В интерфейсе показывается только рабочая пара выбранного HTML: актуальные данные
и предыдущие. Сохранённые данные другого рабочего HTML появляются в его истории
после отката к этому HTML. Предыдущий рабочий HTML явно помечен «Предыдущая».

Предельный общий объём сохранённых данных остаётся примерно **1,5 ГиБ на блок**.
Если после сохранения защищённых пар новый файл не помещается, вся транзакция
откатывается, ранее опубликованные данные остаются. Публикация HTML и откат
доступны и для старого архива, превышающего квоту, поскольку не добавляют байты.
Во время замены и отложенной физической очистки требуется дополнительное место;
учитывайте одновременно загружаемый файл, резервные копии и число блоков.

Очистка старого архива происходит при следующем успешном обновлении, **не по
возрасту** и не при открытии страницы/миграции. Ошибка, конфликт или повтор текущих
данных не удаляют предыдущие версии. Миграция `202609170002_top_dashboard_data_context_state`
только добавляет таблицу сохранённых указателей для возврата к данным другого HTML
и `dashboard_file_cleanup_queue` — транзакционную очередь удаления файлов.
Для старых неактивных HTML, где такие указатели раньше не записывались, первый
успешный переход выбирает две последние совместимые записи; текущая пара всегда
приоритетна. После этого точный выбор, включая откат данных, сохраняется.

Для разовой очистки ранее накопленного архива конкретного блока существует
`scripts/prune-top-dashboard-history.ts`. Оператор сначала делает и проверяет
резервную копию БД и файлов, затем передаёт ID блока и все четыре ожидаемых
указателя (`--html-active`, `--html-previous`, `--data-active`, `--data-previous`;
отсутствующий указатель — `null`). По умолчанию выполняется только проверка с
полным откатом транзакции. `--apply` разрешает удаление после просмотра списка.
Для `--apply` обязателен явно заданный `TOP_DASHBOARD_DATA_DIR`, указывающий на
существующее рабочее хранилище: отдельная shell-сессия не наследует настройку PM2.
Конфликт указателей останавливает операцию. Текущая публикация, её даты, авторы,
черновики и данные рабочего отката не меняются; другие блоки не очищаются.

Задания очистки записываются вместе с удалением версий в одной транзакции, поэтому
падение процесса между COMMIT и файловой очисткой не теряет задания.
Удаление файлов выполняется после COMMIT. Очередь
`.incoming/.pending-deletions` повторяет неудачную очистку; активные ссылки в БД
проверяются заново. Shared-lock существующего backup runner защищает файлы во
время бэкапа и восстановления, при занятом lock загрузка не ждёт бэкап.
Очередь находится в исключённой из бэкапа staging-папке.
Если ответ COMMIT при загрузке потерян, новый файл сохраняется: он может уже
быть действующим. Известные отказы проверки/конфликта/квоты удаляют только новый
непринятый файл, а ранее действовавшая пара остаётся целой.

Изолированные PostgreSQL-проверки: `KTS_TEST_PG_BIN=/path/to/postgres/bin bash scripts/test-top-dashboard-postgres.sh`.
Runner создаёт отдельный временный кластер без TCP и не использует рабочую БД.

После изменения конфигурации обязательно выполнить `sudo nginx -t` и только
после успешной проверки — `sudo systemctl reload nginx`.

Для production-конфига проекта есть идемпотентный helper с резервной копией и
автоматическим откатом при ошибке:

```bash
sudo sh ops/apply-top-dashboard-nginx-limit.sh
```
