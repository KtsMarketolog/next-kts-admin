# KTS: резервное копирование и восстановление

## Статус и согласованные параметры

Новая согласованная политика: **14 суток локально, 5 самых новых проверенных полных
комплектов в Yandex Object Storage**. Облачное хранение считается по комплектам.
При частых преддеплойных копиях все пять могут быть созданы в один день;
минимальная глубина истории в днях не гарантируется.
Это бэкап базы, перечисленных постоянных файлов и конфигурации — **не образ всего VPS**.
По обследованию 12.09.2026 одна проверенная локальная копия занимала около 343 МиБ; 14 ежедневных
комплектов — 4,7 ГиБ, 5 облачных — 1,7 ГиБ. Нужен дополнительный запас на
преддеплойные копии, шестой облачный комплект, временные файлы и тест восстановления.

Оценка 12.09.2026 для облачного хранения с обычным ключом KMS составляла 5–8 ₽/месяц
при обследованном объёме и одной копии в сутки. Она не подтверждает нынешнюю стоимость
и не ограничивает счёт. Рост данных, дополнительные версии ключа, операции и
временное увеличение ёмкости увеличивают расход.

**Новая политика включена и полностью принята в production 15.09.2026.**
Установлен runtime с возможностью отката, а production-конфигурация включает
`retention.localDays: 14`, `cloudRetention.mode: count`, `keep: 5` и явное разрешение
ограниченной очистки. Облако сокращено до пяти полностью проверенных комплектов,
свежее изолированное восстановление и итоговый `check` прошли, лимит бакета возвращён
к 5 ГБ и прочитан обратно. Подробные результаты приведены в датированном разделе ниже.
Историческая приёмка 12.09.2026 относится к прежнему 5-дневному Lifecycle.

Установка сама по себе не включает таймер автоматически и не меняет имеющуюся
конфигурацию. Проверяемый пример по-прежнему содержит `cloudApproved: false`,
`cloudRetention.deleteApproved: false` и `predeployCloudPolicy: required`: он безопасно
выключен для новой установки и не отражает уже настроенную production-конфигурацию.

## Состав комплекта

| Артефакт/источник | Что защищается |
| --- | --- |
| `postgres/<id>.dump` | PostgreSQL custom-format, сжатие 6, без владельцев/ACL |
| `files/<id>.tar.gz`: `uploads/` | `/var/www/kts-uploads`, включая документы клиентов |
| `files/...`: `shared-uploads/` | `/home/kts/kts-next-admin/shared/public/uploads` |
| `files/...`: `top-dashboard/` | `/home/kts/kts-next-admin/shared/runtime-data/top-dashboard` |
| `files/...`: `firmware/` | `/home/kts/kts-next-admin/shared/public/klimatika/prog/firmware/update` |
| `config/<id>.tar.gz` | `.env.local`, Nginx, `postgresql.conf`, PM2 ecosystem |
| `manifests/<id>.json` | Размеры/SHA-256, инвентарь файлов, схема, количества строк, миграции и ссылки БД |

Идентификатор: `kts-next-admin-YYYYMMDDTHHmmssZ-<random>`, время UTC.
Manifest публикуется последним; без него комплект не считается завершённым.
Дамп, количества строк и схема берутся из одного экспортированного snapshot
PostgreSQL. Файлы копируются с проверкой стабильности и связей с snapshot базы.
Это не атомарный снимок всего диска: изменение файла во время копирования
останавливает попытку, а не скрывает возможную несогласованность.

**Не включено:** ОС, пакеты, SSH/TLS закрытые ключи, AWS credentials, IAM/KMS,
почта, GitHub secrets, сторонние сервисы, произвольные каталоги VPS, роли/ACL БД,
`pg_hba.conf` (не читается пользователем приложения). Исходный код восстанавливается
из Git; manifest фиксирует release ID. Нужна независимая сохранность репозитория.

Конфигурационный архив **содержит секреты**. Локальные архивы защищены правами,
но не зашифрованы на уровне файла; облачные объекты должны иметь SSE-KMS.
Не публиковать архивы, env, credentials и диагностические DDL в Git/чат.
SSH/TLS ключи и аварийный доступ к Яндексу хранить отдельно в менеджере секретов.
При потере TLS-ключа допустим перевыпуск сертификата после восстановления DNS.

## Пути, блокировки, хранение

- Runtime: `/home/kts/.local/lib/kts-backup` (не в каталогах релизов).
- Config: `/home/kts/.config/kts-backup/config.json`, владелец `kts`, 600.
- Копии: `/home/kts/backups/kts-next-admin`, каталог 700, файлы 600.
- `state/` — состояния; `receipts/` — подтверждения передачи и сверки.
- Одна `flock`-блокировка `.operation.lock` для всех запусков и установки.
  Отдельная `.upload.lock` защищает сетевые операции. Запускать через `run.sh`.
- Локальная очистка: строго старше `14 * 86400` секунд по UTC `createdAt`, не `find -mtime +14`.
  Она выполняется после успешной операции, поэтому фактический срок может быть длиннее.
  Последний проверенный комплект сохраняется всегда; неподтверждённые облаком
  комплекты сохраняются и вызывают предупреждение/ошибку, а не исчезают молча.
  Перед удалением создаётся приватный устойчивый журнал строго выбранного комплекта.
  После прерывания очистка продолжается по этому журналу с повторной проверкой
  последней исправной копии, путей и подтверждений; чужие файлы не подбираются.
- Порог свободного диска 3 ГиБ останавливает новые операции с ошибкой;
  требуется реакция на уведомление, а не автоматическое удаление старых копий вслепую.
- Включённая count-retention очищает облако до пяти самых новых
  проверенных полных комплектов. Новый комплект сначала загружается и полностью
  проверяется; при уже имеющихся пяти это временно требует места для шестого.
  Перед удалением старых комплектов все пять сохраняемых комплектов скачиваются
  и проверяются по размерам, SHA-256 и SSE-KMS под общей `.operation.lock`.
  Эти полные скачивания создают дополнительный сетевой трафик и операции Storage.
  Устойчивый приватный журнал позволяет безопасно продолжить прерванную очистку
  с повторной проверкой сохраняемых комплектов.
- Неверные manifest, неполные комплекты и объекты без manifest сохраняются и
  требуют уведомления и ручного разбора. Автоматическая очистка по возрасту к ним
  не применяется; срок ожидания перед ручной уборкой согласуется отдельно.
- Уже подтверждённая облаком локальная копия не отправляется повторно после
  удаления из облака по новой политике; локальное хранение остаётся 14 суток.

## Облако и доступы

Существующий отдельный бакет: `kts-next-admin-backups-202609`, предназначенный только
для резервных копий KTS. Префиксы: `postgres/`, `files/`, `config/`, `manifests/`;
`cloud.prefix` пустой. 15.09.2026 лимит временно увеличивался с 5 до 10 ГБ, чтобы
сначала загрузить и проверить новый комплект, а уже затем удалить старые. После
успешной приёмки лимит 5 ГБ сохранён и прочитан обратно; отображавшаяся сразу после
этого статистика 2,2 ГиБ могла оставаться асинхронно устаревшей.

- Endpoint `https://storage.yandexcloud.net`, регион `ru-central1`, профиль `kts-backup`.
- Существующий сервисный аккаунт `kts-backup-sa` (`aje99s18ug92ibqac6bp`).
  `storage.uploader` только на бакете KTS;
  `kms.keys.encrypterDecrypter` только на его KMS-ключе, не на всём каталоге.
  15.09.2026 тому же аккаунту добавлен ACL бакета `READ` + `WRITE`; существующий
  владелец сохранён в bucket policy. Политика разрешает аккаунту на самом бакете
  только `s3:ListBucket`, `s3:GetBucketVersioning`, `s3:GetLifecycleConfiguration`
  и `s3:GetEncryptionConfiguration`, а `s3:GetObject`, `s3:PutObject` и
  `s3:DeleteObject` — только для
  `postgres/kts-next-admin-*`, `files/kts-next-admin-*`,
  `config/kts-next-admin-*` и `manifests/kts-next-admin-*`.
  `FULL_CONTROL`, общие `editor`/`admin`, изменение бакета и изменение KMS аккаунту
  не выдавались. Другие пользователи, сервисные аккаунты, credentials и ключи доступа
  не создавались. У всех 60 существовавших объектов прочитаны пустые ACL без отдельных
  объектных разрешений. Безопасная проверка удаления заведомо отсутствующих ключей
  завершилась успешно во всех четырёх разрешённых префиксах и вернула `AccessDenied` вне их;
  готовые резервные копии этой проверкой не затрагивались. Граница доступа затем
  подтверждена штатной очисткой до пяти комплектов.
  Повторное использование одного ключа имеет компромисс: при его компрометации
  злоумышленник сможет удалять облачные резервные объекты; сохранение последних пяти
  гарантирует штатный скрипт, а не сам ключ. Это не защита от удаления украденным ключом.
- Бакет STANDARD, приватный; публичный доступ к объектам, списку и настройкам выключен.
- Обычный симметричный AES-256 KMS-ключ, не HSM. Используется шифрование бакета
  по умолчанию: перед **каждым PUT** проверяются `aws:kms` и точный KMS ID.
  После PUT сверяются фактическое шифрование объекта, ключ, размер и SHA-256
  скачанных байтов. Несоответствие останавливает комплект без подтверждения receipt.
  Manifest загружается только после проверки трёх архивов; если ошибка выявлена
  при проверке самого manifest после PUT, он уже может существовать в облаке,
  но комплект ещё не считается принятым.
  Ключ `kts-next-admin-backup-key`, ID `abjgv0qpsa5cgg3p8nm2`, защита от удаления включена.
  Настройки KMS и права на ключ при переходе 15.09.2026 не менялись.
  **Удаление KMS-ключа/нужной версии делает соответствующие копии невосстановимыми.**
  Сохранять права расшифровки и платёжный аккаунт, пока нужны копии.
- Versioning выключен. 15.09.2026 установлен и прочитан обратно Lifecycle
  `kts-backups-count-abort-incomplete` из `yandex-lifecycle-count.json`: только отмена
  незавершённых multipart через 1 день, без `Expiration` готовых объектов.
  Lifecycle сам по себе не умеет сохранять пять полных комплектов: это делает runtime.
  Прежний `yandex-lifecycle.json` сохранён как исторический файл; он удаляет объекты
  через 5 дней и не подходит новой политике. Порядок перехода приведён ниже.
  Другие проекты или постоянные файлы в этот бакет не складывать.
  При включении versioning отдельно согласовать сроки noncurrent versions и маркеров.
- AWS CLI v2: `/home/kts/.local/bin/aws`; отдельные файлы
  `/home/kts/.config/kts-backup/aws-config` и `aws-credentials`, 600, пользователь `kts`.
  Ключи вводить/передавать защищённо, не аргументами команд и не через чат.
- Lifecycle и политика доступа применяются правами существующего владельца. Runtime
  продолжает использовать прежний приватный профиль `kts-backup`; администраторские
  роли, публичный доступ и изменение настроек бакета или KMS ему не требуются.
- Облачная очистка удаляет только точно проверенные ключи старых полных комплектов,
  не выполняет массовую синхронизацию с `--delete`. Передаются только завершённые артефакты; запись условная,
  без перезаписи. Проверяются размер, SHA-256 скачанных байтов и KMS ID.
  ETag не используется как MD5. Повторы и таймауты ограничены.
  Яндекс нормализует имена метаданных (`sha256` → `Sha256`): регистр имени
  не учитывается, но неоднозначные дубли отвергаются, значение хеша строго сверяется.
  На приёмке явные SSE-заголовки приводили к `AccessDenied`; документированный
  путь с KMS по умолчанию работает без расширения IAM. Шифрование не отключалось.
  Администратор не должен менять KMS-настройку во время отправки: чтение настройки
  и PUT не атомарны. Runtime-SA менять её не может. Последующая HEAD-проверка
  обнаружит изменение, но не может задним числом зашифровать уже записанный объект.
  Само право `storage.uploader` не даёт удаления объектов; текущий эффективный
  `DeleteObject` разрешён ACL `WRITE` только вместе с ограничивающей bucket policy.
  Право загрузки допускает перезапись:
  `If-None-Match: *` защищает штатную отправку от случайной перезаписи, а не
  от злоумышленника, уже получившего credentials. Это не неизменяемый WORM-архив.
- Текущая реализация ограничивает отдельный артефакт 5 ГиБ и не использует multipart;
  при росте выше лимита нужна отдельная реализация, а не отключение проверки.

## Расписание и ручные команды

Выполнять по SSH **как kts**, не root. Установка: `bash ops/backup/install.sh`
из проверенной копии каталога на сервере. Установщик не очищает старые бэкапы.

AWS CLI установлен отдельно в `/home/kts/.local/aws-cli`: версия 2.36.44,
бинарник `/home/kts/.local/bin/aws`. `install-aws-cli.sh` проверяет PGP-подпись
официального пакета по закреплённому fingerprint AWS и отказывается затирать
существующую установку. Установка не создаёт профиль или ключи доступа.

Первичная настройка использует ту же общую блокировку и фиксированные пути:

```sh
/home/kts/.local/lib/kts-backup/configure.sh policy required
# Через ssh -t, сначала вставить ID, затем секрет в скрытые приглашения:
/home/kts/.local/lib/kts-backup/configure-credentials.sh
# Только после создания бакета/KMS и безопасного сохранения AWS-профиля:
/home/kts/.local/lib/kts-backup/configure.sh cloud BUCKET KMS_KEY_ID
# Только после согласования удаления, проверки ограниченных ACL/bucket policy,
# выключенного versioning и Lifecycle без удаления готовых объектов:
/home/kts/.local/lib/kts-backup/configure.sh retention count 5
```

`configure-credentials.sh` принимает значения только через TTY без эха, без
аргументов и журналирования. Создаёт профиль и credentials с правами 600,
не затирает уже существующие файлы и не включает облако автоматически.
Секрет одноразово показан в консоли Яндекса: не копировать его в чат, историю
команд, screenshots или Git. После успешного ввода очистить буфер обмена.

Последняя команда проверяет приватные локальные файлы профиля, но не доказывает
работоспособность облака: загрузка и восстановление всё равно обязательны.

### Переход с пяти суток на пять комплектов — завершён 15.09.2026

15.09.2026 проверенный runtime, включая `cloud-retention.cjs`, установлен с сохранённой
возможностью отката. Повторно использованы существующие `kts-backup-sa`, профиль и
credentials; новые пользователи, аккаунты и ключи не создавались. Production-конфигурация
атомарно переведена на `retention.localDays: 14`, `retention.cloudCopies: 5` и
`cloudRetention` с `mode: count`, `keep: 5`, `deleteApproved: true`; политика
`predeployCloudPolicy: required` сохранена. Ограниченная политика доступа, ACL,
выключенный versioning и новый Lifecycle без `Expiration` прочитаны обратно. Лимит
бакета на время перехода поднимался до 10 ГБ.

Штатный daily-цикл сначала полностью загрузил и проверил новые копии, затем встроенная
в `sync` очистка проверила пять сохраняемых комплектов и удалила только старейшие
полные комплекты. Отдельной ручной команды облачной очистки не применялось. После
очистки подтверждены ровно пять комплектов, отсутствие незавершённого журнала и
осиротевших объектов; облачное восстановление и независимый `check` прошли, лимит
бакета возвращён с 10 к 5 ГБ. Точные результаты приведены ниже.

`check` отдельно и без удаления проверяет состояние новой политики: число комплектов,
Lifecycle, журнал незавершённой очистки и осиротевшие объекты. Перед удалением runtime
требует отсутствие активного `Expiration`, отключённый versioning и точный KMS-ключ.
Ошибка очистки завершает цикл ошибкой и при `predeployCloudPolicy: required`
останавливает предмиграционный деплой; уже созданный и проверенный новый комплект сохраняется.

Приёмка опирается на фактический production daily, инвентарь облака, восстановление
из Yandex и независимый `check`, а не только на локальные тесты или прежнюю приёмку.

```sh
# Только локальная копия (не заменяет проверку облачного пути):
/home/kts/.local/lib/kts-backup/run.sh capture
# Полный штатный цикл:
/home/kts/.local/lib/kts-backup/run.sh daily
# Передача готовых копий и согласованная облачная очистка после проверки:
/home/kts/.local/lib/kts-backup/run.sh sync
# Изолированная проверка именно облачной копии — выполнять в одном shell как kts:
set -Eeuo pipefail
umask 077
export PATH=/usr/bin:/bin
export XDG_RUNTIME_DIR="/run/user/$(id -u)"
export DBUS_SESSION_BUS_ADDRESS="unix:path=${XDG_RUNTIME_DIR}/bus"
test "$(id -un)" = kts
backup_root=/home/kts/backups/kts-next-admin
exec 7>"${backup_root}/.monitor-restore.lock"
flock --exclusive --wait 60 7
restore_started_epoch="$(date -u +%s)"
systemctl --user start kts-backup-fetch-restore.service
test "$(systemctl --user show kts-backup-fetch-restore.service --property=Result --value)" = success
systemctl --user start kts-backup-restore.service
test "$(systemctl --user show kts-backup-restore.service --property=Result --value)" = success
# Сверить свежий state/restore.json с restore_started_epoch по критериям workflow,
# не выводя manifest, schema-diagnostic или содержимое архивов, затем:
/home/kts/.local/lib/kts-backup/run.sh check
# Журналы без содержимого секретов:
journalctl --user -u kts-backup-fetch-restore.service \
  -u kts-backup-restore.service --since "@${restore_started_epoch}" --no-pager
```

Не применять `--no-block`: оба `systemctl start` должны дождаться завершения oneshot.
Нормальный успешный итог — `Result=success` и `ExecMainStatus=0`; состояние
`inactive/dead` после oneshot допустимо. Финальный `check` также требует активные
таймер и linger и последний `kts-backup.service` с `Result=success`; отдельный ручной
`sync` не заменяет это подтверждение.

Для новой установки после успешной приёмки включить linger (`loginctl enable-linger kts`;
если система требует администратора, выполнить с sudo самостоятельно) и таймер:
`systemctl --user enable --now kts-backup.timer`.
Проверить `loginctl show-user kts -p Linger`, `systemctl --user list-timers`.

## Предмиграционный бэкап

В workflow добавлен вызов `run.sh predeploy` **перед запуском canary**.
Любая ошибка локальной копии останавливает деплой. Владелец выбрал `required`;
он сохранён в конфигурации сервера. Возможные режимы реализации:

- `required` (рекомендуется): нет подтверждённой облачной копии — нет миграции.
- `warn`: после успешного локального бэкапа облачный сбой явно предупреждает,
  но позволяет миграцию. Это осознанный риск потери предмиграционной копии вместе с VPS.
- `pending`: выбранной политики нет, деплой останавливается.

Workflow и режим `required` опубликованы и используются production-деплоем.
Приёмка нового режима успешно завершена; gate не ослаблять. Одна только установленная
конфигурация и в дальнейшем не считается доказательством восстановления.
Откат кода **не откатывает** схему.
Миграции должны сохранять совместимость со старой версией во время canary/rolling deploy.

## Проверка восстановления

Сначала отдельная служба скачивает свежий комплект из облака и проверяет все хеши.
Затем служба восстановления с `RestrictAddressFamilies=AF_UNIX` запускает временный
PostgreSQL 16: собственный каталог, Unix socket, случайное имя БД, отдельная
непривилегированная роль. Production DATABASE_URL не используется как цель.
Лимит RAM 1 ГиБ, CPU 100% одного ядра, пониженный приоритет; минимум доступной
памяти 1 ГиБ. При нехватке перенести проверку на согласованный отдельный runner.

`pg_restore --exit-on-error --single-transaction --no-owner --no-acl`;
сверяются схема, все таблицы и количества строк, миграции, ключевые столбцы,
связи с файлами, SHA-256 всех файлов/config. Архивы tar проверяются потоково,
без извлечения на production-файловые пути. Ссылки и traversal запрещены.
Временный кластер останавливается; очистка разрешена только каталогу с собственным
защитным маркером. При невозможности подтвердить остановку каталог сохраняется.

## Восстановление при полной потере сервера

1. Нужны независимые доступы: GitHub с кодом, Яндекс с бакетом и KMS decrypt,
   действующий KMS-ключ, DNS/хостинг, менеджер секретов. Старого VPS недостаточно
   как единственного места хранения ключей. Пять последних облачных комплектов
   могут охватывать меньше суток; возможно поздно заметить повреждение, уже попавшее
   во все пять копий. Локальные 14 суток недоступны при полной утрате VPS.
2. Создать **новый изолированный сервер**, установить PostgreSQL той же major-версии,
   совместимые Node/PM2/Nginx. Приложение и миграции пока не запускать.
3. Получить целый комплект из `manifests/` и перечисленных в нём объектов.
   Сверить размеры и SHA-256 каждого скачанного артефакта, SSE-KMS, `pg_restore --list`.
   Не смешивать разные ID. Использовать downloadLatest и изолированный drill
   на новом сервере с проверенной, адаптированной конфигурацией путей.
4. Создать чистую целевую БД и прикладную роль; роли/пароли не содержатся в дампе.
   В отдельной защищённой сессии задать новый пароль (`psql` → `\password`),
   не печатать пароль в командной строке. Восстановить custom-дамп строго в новую БД
   с `--exit-on-error --single-transaction --no-owner --no-acl`, от прикладной роли.
   Администратор заранее готовит расширения/права, если это потребуется.
5. Проверить tar-инвентарь штатным verifier. Только после этого извлечь архивы
   в приватный staging на новом сервере, не прямо в `/`. Скопировать четыре
   источника согласно таблице путей. Назначить владельца `kts`; документы
   и runtime-data не должны быть доступны через публичную директорию Nginx.
6. Из config-архива восстановить `.env.local` с правами 600, адаптировать реквизиты
   новой БД/SMTP. Пересмотреть Nginx, PM2, PostgreSQL, а не слепо заменить конфиги.
   `pg_hba.conf` воссоздать с localhost/scram и без внешнего доступа; TLS перевыпустить.
   После компрометации старого сервера заменить все связанные секреты.
7. Собрать зафиксированную версию приложения из Git и связать постоянные каталоги.
   Сопоставить schema_migrations с manifest; не запускать новые миграции автоматически
   до проверки восстановления. Проверить вход, каталог, документы, загрузки и дашборды.
8. Только после приёмки направить трафик/DNS на новый сервер. Повторно настроить
   бэкапы, независимый монитор, SSH host pin и аварийные доступы.
