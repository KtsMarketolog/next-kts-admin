# Независимый контроль резервных копий КТС

Workflow `.github/workflows/backup-health.yml` выполняется на GitHub-hosted runner, отдельно от VPS. Сроки хранения, согласованные для этого проекта: **14 суток локально, 5 суток в Yandex Object Storage**. Workflow не меняет Lifecycle и не запускает очистку.

| Проверка | UTC | Москва | Что запускается |
| --- | --- | --- | --- |
| Ежедневная | 03:45 | 06:45 | `/home/kts/.local/lib/kts-backup/run.sh check` |
| Пробное восстановление | воскресенье 04:30 | воскресенье 07:30 | `kts-backup-fetch-restore.service`, затем `kts-backup-restore.service`, затем полная проверка |

Плановое время задаётся cron GitHub; фактический старт может задержаться. Группа concurrency исключает одновременные workflow, активная проверка не отменяется следующим запуском. Автоматические запуски начнутся после попадания workflow в основную ветку и при включённых GitHub Actions. Неполная настройка приводит к ошибке, а не к молчаливому пропуску.

## Что проверяется

Серверный `check` проверяет последнюю завершённую копию и состояние последней попытки, возраст до 30 часов, владельца и права 600, размеры и SHA-256 всех архивов, читаемость PostgreSQL custom-архива, включённый/активный таймер, успешный результат службы, linger, свободный диск, зависшие временные каталоги старше двух часов. Облачная проверка подтверждает соответствующий объект, его размер, SHA-256 скачанных данных и SSE-KMS. Также обязательно успешное восстановление именно из облака не старше 8 дней; отсутствующая, незавершённая или неуспешная последняя попытка вызывает ошибку.

Воскресный запуск сначала скачивает полный набор именно из Yandex. После завершения download-службы запускает изолированное восстановление через отдельную службу с `RestrictAddressFamilies=AF_UNIX`. Проверяет успешное завершение обеих служб и свежий отчёт `state/restore.json` с `origin=yandex`, после чего выполняет полный `check`. Этот порядок позволяет выполнить первое восстановление или исправить устаревший/неуспешный drill, который сам по себе не прошёл бы предварительный `check`. Старый успешный отчёт не засчитывается. Отчёт в GitHub содержит только ID набора, время, количество таблиц/строк/файлов, размеры и контрольные суммы архивов; содержимое базы, файлов и конфигурации в GitHub не копируется.

## Необходимые настройки GitHub

Репозиторий: `KtsMarketolog/next-kts-admin` → Settings → Secrets and variables → Actions. Уже используемые секреты деплоя:

- `VPS_HOST`: проверяется на точное соответствие `62.217.177.155`.
- `VPS_USER`: проверяется на точное соответствие `kts`.
- `VPS_SSH_KEY`: приватный ключ для существующего разрешённого доступа пользователя kts. В Git не хранить; runner создаёт временный файл с правами 600 и удаляет его при завершении.

Для письма **независимо от доступности VPS** нужны отдельные GitHub secrets:

| Secret | Значение |
| --- | --- |
| `BACKUP_SMTP_HOST` | SMTP-сервер согласованного отправителя |
| `BACKUP_SMTP_USER` | SMTP-логин |
| `BACKUP_SMTP_PASSWORD` | Пароль приложения для SMTP; никогда не вставлять в переписку |
| `BACKUP_SMTP_PORT` | Обычно 465 (по умолчанию) либо 587 |
| `BACKUP_SMTP_SECURE` | `true` для TLS на 465; `false` для STARTTLS на 587 |
| `BACKUP_SMTP_FROM` | Необязательно: разрешённый отправитель; по умолчанию SMTP_USER |

Адрес получателя зафиксирован в `ops/backup/notify.cjs`: **ktsmarketolog@yandex.ru**. Письма при успехе не отправляются, кроме явно выбранного ручного теста. Ошибка или таймаут SSH тоже запускает отдельный job уведомления. Он устанавливает самостоятельный runtime из `ops/backup/package-lock.json` командой `npm ci --prefix ops/backup --ignore-scripts --omit=dev`; ключ кэша использует тот же lock-файл. Используется собственный notifier; сторонних mailer actions нет.

## Проверка после настройки

1. Открыть Actions → **KTS backup monitor** → Run workflow → `mode=restore`, `test_email=true`. Так создаётся первая проверенная история восстановления и затем выполняется полный контроль.
2. Убедиться, что оба job успешны и письмо действительно пришло на ktsmarketolog@yandex.ru. Один успешный SMTP-ответ без проверки почтового ящика ещё не доказывает доставку во «Входящие».
3. Проверить свежий `restore-verified`, `origin=yandex`, а затем отдельно выполнить `mode=check`, `test_email=false`. Проверка должна подтвердить в том числе новое облачное восстановление и успешно завершиться.
4. Для контролируемой проверки отказа SSH использовать отдельную тестовую ветку с SSH-назначением `127.0.0.1:1` внутри GitHub runner и `mode=check`; не менять production secrets или закреплённый ключ основной ветки. Проверка должна стать красной, а job `Independent failure email` — отправить письмо. Тестовую ветку не сливать. Именно так выполнен приёмочный `TEST ONLY`.

Журналы на сервере:

```bash
journalctl --user -u kts-backup.service -u kts-backup-fetch-restore.service -u kts-backup-restore.service --since today
systemctl --user list-timers kts-backup.timer
```

Письмо содержит ссылку на конкретный GitHub run. Ошибку проверять по этой ссылке и journald. Не публиковать `state/schema-diagnostic.json`, дампы, `.env.local`, AWS credentials или содержимое архивов в Actions artifacts/issue/переписку.

## Ограничения

Независимый workflow проверяет работоспособность существующей схемы бэкапа, а не создаёт копию всего сервера. Он не меняет тарифы, IAM, бакет, KMS или production-базу. Если одновременно недоступны GitHub Actions и VPS, этот канал не сможет прислать письмо; для защиты от отказа самого планировщика нужен отдельный внешний heartbeat-сервис. Срок в облаке 5 дней означает более короткую защиту при утрате VPS, чем локальные 14 дней.
