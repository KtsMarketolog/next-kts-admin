# Независимый контроль резервных копий КТС

Workflow `.github/workflows/backup-health.yml` выполняется на GitHub-hosted runner, отдельно от VPS. Новая согласованная политика: **14 суток локально, 5 самых новых проверенных полных комплектов в Yandex Object Storage**. Все пять могут быть созданы в один день при частых деплоях; глубина облачной истории в днях не гарантируется. Workflow не меняет Lifecycle и не запускает очистку.

**Политика включена и полностью принята в production 15.09.2026.**
Установлен runtime с возможностью отката, production-конфигурация включает
`retention.localDays: 14`, `cloudRetention.mode: count`, `keep: 5` и
`deleteApproved: true`, а Lifecycle отменяет только незавершённые multipart через сутки
и не содержит `Expiration`. Лимит бакета временно увеличивался с 5 до 10 ГБ и после
приёмки возвращён к 5 ГБ. Фактически подтверждены пять полных облачных комплектов,
свежее восстановление и полный `check`. Результаты 12.09.2026 ниже относятся к прежней
политике пяти суток. Полный отчёт приведён в [README.md](README.md).

Плановое время задаётся cron GitHub; фактический старт может задерживаться. Группа concurrency исключает одновременные workflow, активная проверка не отменяется следующим запуском. Автоматические запуски выполняются из основной ветки при включённых GitHub Actions. Неполная настройка приводит к ошибке, а не к молчаливому пропуску.

## Что проверяется

Серверный `check` проверяет последнюю завершённую копию и состояние последней попытки, возраст до 30 часов, владельца и права 600, размеры и SHA-256 всех архивов, читаемость PostgreSQL custom-архива, включённый/активный таймер, успешный результат службы, linger, свободный диск, зависшие временные каталоги старше двух часов. Облачная проверка подтверждает соответствующий объект, его размер, SHA-256 скачанных данных и SSE-KMS. Также обязательно успешное восстановление именно из облака не старше 8 дней; отсутствующая, незавершённая или неуспешная последняя попытка вызывает ошибку.

Новая очистка в штатном цикле работает под общей `.operation.lock` и до удаления
скачивает и полностью проверяет все пять сохраняемых комплектов. При уже имеющихся
пяти комплектах требуется место для шестого. Полные скачивания добавляют сетевой
трафик и операции Storage. Очистка встроена в `run.sh sync`; отдельной команды для неё нет.
Перед удалением проверяются отсутствие активного `Expiration`, отключённый versioning
и точный KMS-ключ. Приватный устойчивый журнал защищает
продолжение прерванной очистки. Неполные комплекты, неверные manifest и объекты без
manifest сохраняются, вызывают уведомление и требуют ручного разбора; срок ожидания
перед их ручной уборкой согласуется отдельно. Ошибка очистки вызывает ошибку цикла и
останавливает предмиграционный деплой при сохранённой политике `required`; уже проверенная
новая копия остаётся. `check` без удаления проверяет число комплектов, облачную политику,
журнал незавершённой очистки и осиротевшие объекты. Приёмка 15.09.2026 подтвердила
совместно Lifecycle, конфигурацию, фактическую очистку, свежую копию и drill. При будущих
проверках один успешный этап сам по себе по-прежнему не заменяет весь этот набор.

Используются прежние `kts-backup-sa`, профиль и credentials `kts-backup`; другие
пользователи, аккаунты и ключи не создавались. 15.09.2026 аккаунту добавлен ACL бакета
`READ` + `WRITE`, а bucket policy сохранила существующего владельца и ограничила runtime:
на бакете — `ListBucket`, `GetBucketVersioning`, `GetLifecycleConfiguration` и
`GetEncryptionConfiguration`; над объектами — `GetObject`, `PutObject`, `DeleteObject`
только для `postgres/kts-next-admin-*`, `files/kts-next-admin-*`,
`config/kts-next-admin-*` и `manifests/kts-next-admin-*`. KMS не менялся,
versioning выключен, ACL всех 60 существовавших объектов пусты. Удаление заведомо
отсутствующего ключа вернуло HTTP 200 в каждом из четырёх разрешённых префиксов и
`AccessDenied` вне их; готовые копии тестом не затрагивались. Lifecycle
`kts-backups-count-abort-incomplete` отменяет незавершённые multipart через сутки и
не имеет `Expiration`. Эти readback-проверки и фактическая штатная очистка подтвердили
границы доступа. Бакет остаётся приватным с SSE-KMS, без новых административных ролей
у runtime и без доступа к другим проектам; существующая IAM-роль `storage.uploader`
на бакете сохранена.

Воскресный запуск сначала скачивает полный набор именно из Yandex. После завершения download-службы запускает изолированное восстановление через отдельную службу с `RestrictAddressFamilies=AF_UNIX`. Проверяет успешное завершение обеих служб и свежий отчёт `state/restore.json` с `origin=yandex`, после чего выполняет полный `check`. Этот порядок позволяет выполнить первое восстановление или исправить устаревший/неуспешный drill, который сам по себе не прошёл бы предварительный `check`. Старый успешный отчёт не засчитывается. Отчёт в GitHub содержит только ID набора, время, количество таблиц/строк/файлов, размеры и контрольные суммы архивов; содержимое базы, файлов и конфигурации в GitHub не копируется.

1. Открыть Actions → **KTS backup monitor** → Run workflow → `mode=restore`,
   `test_email=false`. Убедиться, что download-служба и restore-служба успешны,
   опубликован свежий `restore-verified` с `origin=yandex`, а последующий полный

2. При необходимости отдельно выполнить `mode=check`, `test_email=false`; он должен
   подтвердить свежую копию, count-retention, Lifecycle, KMS, таймер и недавний drill.
3. `test_email=true` использовать только для осознанной повторной проверки доставки.
   Для приёмки 15.09.2026 новое тестовое письмо не требовалось: email-канал уже был
   подтверждён во «Входящих», а существующий неуспешный
   [run 34949825922](https://github.com/KtsMarketolog/next-kts-admin/actions/runs/34949825922)
   в тот же день завершил job `Independent failure email` успешно.

Контролируемую проверку отказа SSH при необходимости выполнять только в отдельной
тестовой ветке с назначением `127.0.0.1:1` внутри GitHub runner; production secrets и
закреплённый ключ основной ветки не менять, тестовую ветку не сливать.

Журналы на сервере:

```bash
journalctl --user -u kts-backup.service -u kts-backup-fetch-restore.service -u kts-backup-restore.service --since today
systemctl --user list-timers kts-backup.timer
```

Письмо содержит ссылку на конкретный GitHub run. Ошибку проверять по этой ссылке и journald. Не публиковать `state/schema-diagnostic.json`, дампы, `.env.local`, AWS credentials или содержимое архивов в Actions artifacts/issue/переписку.

## Ограничения

Независимый workflow проверяет работоспособность существующей схемы бэкапа, а не создаёт копию всего сервера. Он не меняет тарифы, IAM, бакет, KMS или production-базу. Если одновременно недоступны GitHub Actions и VPS, этот канал не сможет прислать письмо; для защиты от отказа самого планировщика нужен отдельный внешний heartbeat-сервис. Пять последних облачных комплектов не гарантируют пяти дней истории: частые деплои могут заменить их за один день. При утрате VPS локальные 14 суток истории также будут потеряны.
